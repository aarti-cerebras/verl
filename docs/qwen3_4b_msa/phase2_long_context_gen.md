## 1. Scope and decisions

Carried over from [`phase2_long_context_data.md`](phase2_long_context_data.md) §2c (user, 2026-08-10):

1. **Phase 2b only.** Base unfrozen, `L_LM + λ·Σ L_KL` (+ minority BC).
2. **Prompts only.** Every column except the prompt is discarded; responses are generated by
   Qwen3-4B-Thinking-2507 in reasoning mode.
3. **No 32K cap on kept sequences.**

New decisions (user, 2026-08-10), which are what this document is for:

4. **Total sequence length per sample = 131,072 tokens** (prompt + generated trace + terminator).
   *This is a total-window decision, not an output-budget decision* — an earlier reading of "128K
   output tokens" would have needed `max_model_len` 262,144 and is superseded.
5. **Collect all realized lengths.** No length-based filtering, no bucketing, no subsampling at
   generation time. The parquet spans short → 131K and the Phase-2b mixture is cut from it *later*.
6. **ChatQA2 included, but segregated and licence-tagged** — generated into its own artifact directory
   so the NC-encumbered rows can be included or dropped at training-mix time without regenerating.
7. **All languages kept, `lang` recorded per row.** No English filter; the mix is a training-time
   decision.
8. **Pilot gates the full run.** No large GPU spend until the pilot's measured numbers are reviewed.

Decisions 5–8 all point the same way: **push every choice that can be deferred past generation into the
parquet as a column**, because generation is the expensive, hard-to-repeat step and everything
downstream of it is cheap.

### 2.1 The 131,072 window prunes the top of two sources

Decision 4 is a **total** window, so a prompt near 131K leaves no room to answer. Two sources have mass
there:

- **`ChatQA2/NarrativeQA_131072`** — p90 is **131,167**, i.e. at least ~10% of the config sits at or
  above the whole window. The config name is literal: it was built *to* 131,072 with a Llama-3
  tokenizer, and Qwen3 retokenization pushes much of it over. **Measured worse than estimated:** in a
  237-row sequential sample, **37% (87 rows) fell below the 8,192-token generation floor**, clustered
  at 125,885–131,195 prefill tokens — a 25-distinct-length pile against NVIDIA's truncation wall, not a
  natural distribution. That sample is biased (§4.1b), so the true rate needs the full extraction.
  **Resolved by §2.2 — Tier B's window is raised rather than the rows dropped.**
- **`LongCite-45k`** — max 138,127, but p90 is only 73,323, so the affected tail is small (est. 1–3%).

This needs an explicit floor, not just the existing `cap <= 0` skip (§5.2): a row that survives with a
900-token generation budget is a truncated-trace factory, and under decision 5 we keep everything, so
those rows would pollute the pool rather than being silently dropped later. **`--min-gen-budget 8192`**,
with the skip count logged per source. Rows below the floor are written to a `skipped_nofit.jsonl`
sidecar rather than dropped silently, so the decision is revisitable without re-reading the sources.

### 2.2 Tier B runs at a 163,840 window (user, 2026-08-11)

Rather than lose the band ChatQA2 was included for, **Tier B's window is raised to 163,840**; Tier A
stays at 131,072. The tiers were already separate runs (decision 6), and `--window` is per-invocation,
so this costs no new code — only provenance, which is why every row now carries `window` and
`min_gen_budget` columns.

Why 163,840 and not the model's native 262,144:

| window | KV / seq | concurrent / H200 | budget at 131,195 prefill |
|--:|--:|--:|--:|
| 131,072 | 18.0 GiB | 6.4 | **−134 (rejected)** |
| 147,456 | 20.2 GiB | 5.6 | 16,250 |
| **163,840** | **22.5 GiB** | **5.1** | **32,634** |
| 196,608 | 27.0 GiB | 4.2 | 65,402 |
| 262,144 | 36.0 GiB | 3.2 | 130,938 |

- **The prompts cannot run away.** NVIDIA capped these documents at 131,072 *Llama-3* tokens, so Qwen3
  prefill is bounded by the retokenization ratio — observed max 131,195 (1.001×). Even a pessimistic
  1.10× would need only a 152,382 window. 163,840 covers that with headroom.
- **32,634 tokens of generation budget is a proven size**, not a guess: it is the same budget the Dolci
  pilot ran at (trace p50 20,669, 8% truncation on the hardest slice), and NarrativeQA answers are
  short — the length here is prefill, not decode.
- **262,144 buys nothing and costs half the concurrency.** Throughput at this context is KV-bandwidth
  bound (§5.4), so concurrency is throughput.

**The consequence to keep visible:** Tier B rows can now exceed 131,072 *total*. Prefill is ~131K and
NarrativeQA traces should be short, so expect most to land ~133–138K rather than near 163,840 — but
Phase 2b must either train those rows at a ≥140K window or drop them at mixture time. That is exactly
the choice decision 5 defers, and the `window` column is what makes it decidable later. It does mean
**Tier B is not drop-in usable at a 128K training window**, which Tier A is.

## 4. Prompt extraction contract

**Step 0 is DONE (2026-08-10).** All seven schemas dumped from `datasets-server /info` + real rows;
the column names below are **measured, not inferred**. Cell contents were not truncated at the sizes
sampled, but the extractors must still read **parquet row groups directly** for the full pass —
`/rows` truncates long cells in general (`phase2_long_context_data.md` §0 trap 2) and strided sampling

Common contract, identical to `phase2_data_gen.md` §4 so that `gen_trajectories.py` needs no change:

```json
{"source_uid": "...", "source_dataset": "zai-org/LongCite-45k", "source_config": "...",
```

Two fields are new relative to the Dolci path: **`licence_tier`** (decision 6) and **`lang`** promoted

what `gen_trajectories.py`'s per-domain cap lookup and `analyze_lengths.py --group-by domain` already

Six findings from step 0 that were **not** in the survey and that change the extractors:

1. **`LoongRL` and `DocQA-RL` share one verl RL schema** → one backend, two configs. For LoongRL use
   `prompt`, **not** `context`: `context` is the *un-injected* base passage (58,920 chars in the sampled
   row) while `prompt` (66,837 chars) is the KeyChain-injected version with the
   `{"<uuid>": "<uuid>"}` pairs inlined into the passage text. Extracting `context` would silently
   discard the task. `extra_info.input_question` carries the real question and
   `reward_model.ground_truth` the answer — both metadata only.
2. **`ChatQA2`, `DocQA-RL` and `LongReward` ship `test`/`dpo` splits alongside the training split.**
   ChatQA2 has `test` on *both* configs (6,765 + 32,001 rows). **Use `train` only** — pulling prompts
   from a held-out split is self-contamination, and nothing in the survey flags it because the survey
   measured lengths, not splits.
3. **`ChatQA2/sub-paragraphs` has mojibake as well as the Llama-3 marker.** The sampled row begins
   `<|begin_of_text|>ï»¿The Project Gutenberg EBook of Percival Keene…` — that `ï»¿` is a UTF-8 BOM
   mis-decoded as latin-1, upstream in NVIDIA's own data. Strip the marker **and** repair the encoding;
   otherwise every Gutenberg-derived row starts with junk tokens. Count and log both.
4. **`LongAlpaca-12k` needs no join**: `input` and `file` are `null`, and `instruction` already holds
   document + question. It does carry its own light preamble (*"Below is a paper. Memorize the paper and
   answer my question after the paper."*) — **keep it**, unlike LongCite's: it is a plain natural-language
   framing, it injects nothing into the document body, and it is ~20 tokens rather than 9.7% of the row.
5. **`LongReward`'s `win_response`/`lose_response` are the literal string `"none"` in the `sft` split**
   (they belong to the `dpo_*` splits). Nothing to discard, but a backend that assumes they are real
   text will produce garbage. The sampled row is also **cross-lingual** — English context, Chinese query
   — confirming the survey's note; under decision 7 these are kept and tagged.
6. **`LongAlign-10k` is `messages`, not a flat prompt**, so the multi-turn drop rule (below) is
   load-bearing for this source specifically rather than a formality. Its `length` column is the
   ChatGLM3 count (63,954 on row 0 vs 53,176 Qwen3) — trap 1; **never** use it for bucketing.

`smoltalk2` is not extracted at all (§2c.1 — strictly dominated by `LongAlign-10k` once traces are
discarded).

### 4.1b Three more findings, from building the extractors (2026-08-11)

Step 0 read `/info` and one row per *dataset*. Implementing against real data surfaced three things it
had missed, two of which are silent-data-loss bugs.

1. **The datasets-server parquet conversion is PARTIAL for the two largest sources.** LongCite converts
   2.52 GB of 5.73 GB native; ChatQA2 converts 4.42 GB of 17.34 GB. Reading the parquet branch would
   have silently dropped roughly **half of LongCite** — 60% of the Tier A pool — with no error. Both
   now read **native files** instead (`long.jsonl`; ChatQA2's two `*_QA_train.json` arrays streamed
   with `ijson`, since they are 8.7 GB and 5.6 GB). The other five sources convert fully and use
   parquet. `list_parquet_files()` warns whenever it sees a `partial-` path.
2. **ChatQA2's two configs share column *names* but not layout** — and blindly concatenating would
   manufacture the exact pathology §6 filters for:

   | | `NarrativeQA_131072` | `long_sft` |
   |---|---|---|
   | `sub-paragraphs` | the document (to ~552 KB) | **empty** |
   | `question` | bare (*"Who is Miss Delmer?"*) | **the entire prompt** — instruction + `Article:` + document + `Question:` |
   | wrapper | none | `User: … \n\nAssistant:` |

   Left alone, every `long_sft` prompt would end in a fake `Assistant:` role marker immediately before
   Qwen3's own `<|im_start|>assistant`. The extractor dispatches on content, not config name, so a
   mixed row is handled either way.
3. **NarrativeQA asks many questions per document, and prefill is the dominant cost.** In a 237-row
   sequential sample, **140 rows (59%) repeated an already-seen document** and 3 were exact duplicates.
   Each repeat re-pays for ~130K tokens of the same text. New `--max-per-document N` caps rows sharing
   a document (keyed on a hash of the prompt head, so it works for every source, not just those with a
   usable id). **Tier B's real cost is set by this flag**, and the row counts in §2 overstate document
   diversity accordingly.

Two smaller ones: ChatQA2 needed mojibake repair on **25%** of sampled rows, not just the head of
Gutenberg files; and `--limit-per-source` reads sequentially from row 0, which is trap 3 — it is a
smoke-test flag only, and the code now warns loudly. **The pilot set must be drawn from a full
extraction**, not from a capped read.

### 4.2 Why LongCite is stripped — the one real preprocessing step

Measured over 20 rows / 275,352 prompt tokens (2026-08-10): the citation preamble is **109 tokens,
present in 20/20 rows**; the `<C{i}>` markers are **9.7% of prompt tokens** (range 6–14%) at a density
of **one every ~35–70 tokens**; **0/20 questions reference chunk IDs**, so the question stands alone
after removal. `<C13>` tokenizes as `['<C','1','3','>']`.

Four reasons, strongest first:

1. **The markers are periodic artificial attention landmarks, and learning where to attend is the whole
   job.** `<C` is a lexically unique, low-entropy token recurring every ~50 positions through the entire
   document. The indexer is trained by KL against dense attention *on these sequences*, so whatever
   marker-conditioned selection policy dense attention exhibits gets cloned — and then deployed against
   RULER / NoLiMa / HELMET and real documents, none of which contain markers. That is a train/serve
   mismatch **in the attention-selection policy itself**, on top of the document-QA-vs-synthetic-retrieval
   mismatch `phase2_long_context_data.md` §11 already names as the project's core risk.
2. **LongCite is ~60% of the prefill-long pool**, so its template becomes the bucket's dominant template.
   Stripped, it looks like LongReward / LongAlign / ChatQA2 and joins the pool instead of defining it.
3. **It would spend the BC budget on a format we neither want nor evaluate** — Qwen3 would learn to emit
   `<statement>…<cite>[12-12]</cite></statement>`.
4. **Probable yield loss on the most expensive rows.** An unfamiliar structured citation format over a
   20–70K document is a good candidate for elevated malformed output, dropped by §6 *after* paying the
   full prefill cost.

Caveats, recorded so they are not re-derived: stripping is itself a template choice, not a return to
nature; markers and the `<cite>[i-j]` response format are one coupled system, so it is all-or-nothing
per row; and a naive `re.sub(r'<C_?\d+>', '', text)` would also eat legitimate occurrences in chemistry,
code or markup — **log the removal rate per row and assert it lands in the measured 6–14% band**, so an
over-eager stripper fails loudly instead of quietly deleting content (§9 test 1).

### 4.3 Shared hygiene

Reusing `select_prompts.py`'s existing machinery:

1. **Exact-match sha256 dedup**, within and across sources — LongCite/LongAlign/LongReward draw on
   overlapping public document pools, and LoongRL's three configs share a Wikipedia base. Dedup runs
   **before** generation so a duplicate never becomes duplicated GPU time (`phase2_data_gen.md` §1.1).
2. **Multi-turn drop** — same rule as §4 step 2 there; Qwen3's template strips reasoning from
   non-final assistant turns, so a multi-turn row trains on a mutilated history.
3. **`lang` tagging** by CJK codepoint share, threshold recorded. Expected shares to reproduce as a
   regression check: LongCite 46.5%, LongReward 43.5%, LongAlign 26.1%.
4. **`--exclude-sha`** against the frozen Phase-2 val list *and* the eval-gate hashes.
5. `prompt_tokens` recorded with the Qwen3 tokenizer at selection time, which is what §5.2's floor needs.

### 5.1 The 131,072 window, exactly

Same wrapper arithmetic as `phase2_data_gen.md` §5.1 — 10 prefix tokens + 1 closing `<|im_end|>`.
**The code does not rely on the constant**: `--fit-window` computes `len(prefix_ids)` live per row, and
the converter re-derives and asserts it, so a template change fails loudly rather than silently
misaligning the mask. (The constant is documentation; verifying it is §9 test 7.)

| prefill band | rows (est.) | generation budget |
|---|--:|--:|
| 16–32K | ~40% | ~99K–115K |
| 32–64K | ~30% | ~67K–99K |
| 64–128K | ~25% | ~3K–67K |
| >123K | ~5% | **below floor → skipped (§2.1)** |

Qwen3-4B-Thinking's card recommends an ~81,920-token output budget, so **every row above ~49K prefill
gets less than the card's recommendation**, and rows in the 100K+ band get far less. That is the real
cost of decision 4 and it is worth stating plainly: on the longest prompts we are measuring a
*budget-constrained* trace, not the model's natural one. The pilot measures the truncation rate by
prefill band (§10) so this is quantified rather than assumed.

### 5.2 The budget floor

`gen_trajectories.py` currently skips only when `cap <= 0` and logs a bare count. Needed:
`--min-gen-budget N`, rows below it written to `skipped_nofit.jsonl` with their prefill length, and a
per-source skip table in the run log.

### 5.3 Cost — a calculation, not a measurement

The binding number is unmeasured; this is arithmetic to size the pilot, and §10 replaces it.

*Prefill.* Per token the linear layers cost ~8 GFLOP; attention costs `4·n_heads·head_dim·ctx` ≈
**38 GFLOP at 64K context**, so attention dominates ~5:1 and the cost is strongly superlinear in
context. At a nominal 450 TFLOPS achieved that is ~10K tok/s/GPU ≈ 80K tok/s node at 64K average.

| | prefill tokens | est. prefill wall-clock |
|---|--:|--:|
| Tier A | 1.58B | **~5.5 h** |
| Tier B (ChatQA2) | 2.57B | ~9 h |
| both | 4.15B | **~14.5 h** |

*Decode.* **Unknown, and it is the number that decides everything.** These are document-QA prompts, so
the length is in the prefill and traces may be short — but LoongRL is a task the 4B model likely fails,
and models fail long tasks by rambling. If p50 response is 5K, Tier A adds ~210M output tokens; if it is
20K, ~840M. At long context, decode is KV-bandwidth-bound (§5.4), so this could plausibly range from
~10 h to several days for Tier A alone.

**This spread is the entire justification for decision 8.** Do not launch either tier before §10.

### 5.4 KV cache and preemption — the failure mode to design against

Measured from the model config: 36 layers × 8 KV heads × 128 head_dim × 2 (K+V) × 2 bytes =
**147,456 B/token = 144 KiB/token**.

| context | KV per sequence |
|--:|--:|
| 32,768 | 4.5 GiB |
| 131,072 | **18.0 GiB** |

On a 143 GB H200 at `gpu_memory_utilization=0.90`: ~129 GB, minus ~8 GB weights and ~4 GB
activations/CUDA graphs → **~117 GB of KV ≈ 6 full-length sequences per GPU**, ~48 across the node.

The hazard: if the scheduler admits more sequences than KV allows, vLLM **preempts and recomputes** —
and recomputing a 100K-token prefill is catastrophic, turning a slow run into a stalled one. It is also
easy to miss, because it shows up as bad throughput rather than an error. Mitigations, all in the plan:

- expose and set **`--max-num-seqs`** (not currently a flag) to something the KV budget can actually
  hold;
- **log vLLM's preemption counter** per chunk — a nonzero value is a pilot-gate failure, not a warning;
- keep **DP=8 / TP=1**. TP=2 would halve KV per GPU but also halve the replica count, leaving total KV
  unchanged while adding all-reduce overhead to a 4B model.

## 6. Filters

The ten malformed-response classes of `phase2_data_gen.md` §7 apply **unchanged**, on token IDs, with
per-class counters per source. Marker IDs: `<think>` 151667 · `</think>` 151668 · `<|im_start|>` 151644 ·
`<|im_end|>` 151645. Two policies restated because they are easy to erode: **never filter on answer
correctness**, and **drop, do not repair**.

Three points specific to this run:

### 6.1 Truncation should be rare, and where it is not, that is the finding

The Dolci pilot measured 8% `finish_reason == "length"` for Math and Code at a 32K window. Here the
budget is 3–14× larger for most rows, so the rate should collapse — **except** in the 100K+ prefill band
where the budget is smaller than 32K (§5.1). Report truncation **by prefill band**, not just by source;
a flat average would hide exactly the population the window hurts.

### 6.2 LoongRL will fail the task, and that is fine

`phase2_long_context_data.md` §2b is unambiguous: this is behaviour cloning, so a low KeyChain pass rate
is a diagnostic, not a defect — if dense Qwen3-4B-Thinking fails it, we *want* the sparse model to fail
it identically. What *is* a yield question is the **pathology rate**: a model that cannot do a task
tends to ramble to the cap, and those rows are dropped by the standard filters. Track LoongRL's
truncation and repetition rates separately; if they are extreme, that is an argument about how much
LoongRL to include, decided at mixture time (decision 5).

### 6.3 The repetition detector needs re-checking at this scale

The n-gram detector (any 32-token n-gram repeated ≥8×, or >30% of the trace inside repeats) was tuned on
≤32K traces. On a 100K trace, legitimate long-form output can trip a fixed absolute count. Re-validate
the thresholds against pilot traces before the full run, and log the score distribution, not just the
pass/fail.

### 7.1 Prompt selection streams to disk (fixed 2026-08-11)

The first Tier A run buffered all six pools in memory and wrote only at the end: **8.9 GB RSS**, and a
crash before the last source would have discarded ~50 minutes of tokenization for nothing. ChatQA2 is
2.4× the source bytes, so Tier B would have been worse.

`collect_longctx` now takes an `emit` callback and **writes each row as it is accepted**. What stays
resident is per-source scalars and the cross-source dedup state — which is hashes, not text. The output
is flushed every 2,000 rows and fsynced at the end, so an interrupted run leaves a readable prefix.

What made this possible is dropping the per-source `rng.shuffle(pool)`, which is safe **for this
backend specifically**: unlike the ultradata/dolci-rl paths there is no `pool[:count]` truncation
downstream (every row is written), `sample_prompts_stratified.py` re-samples with its own RNG, and
`gen_trajectories`' `prompts[rank::N]` striding spreads each source across all DP replicas regardless
of within-source order. Rows are emitted in arrival order. Verified against the buffered
implementation on a full 1,591-row source: **identical content, 0 rows differing**, order changed as
expected.
