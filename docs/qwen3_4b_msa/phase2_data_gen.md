# Qwen3-4B MSA — Phase-2 data generation from `allenai/Dolci-Think-RL-32B`

Concrete build plan for the **short + decode-long** halves of the Phase-2 mixture
(`../qwen3_4b_dsa/data_plan.md` §5, streams **S2** and **S3**). The prefill-long half (**S1**) is
unchanged: `examples/dsa/prepare_real_data.py` long documents, already built and already used by
Phase 1 / Phase 2a.

**Governing rule (unchanged, user-reaffirmed 2026-07-30): prompts only.** Every column of this
dataset except `prompt` is discarded for training purposes. Responses are generated by
**Qwen3-4B-Thinking-2507** (`/cb/ml-eng/aarti/models/qwen3_4b_thinking_2507`). Rationale:
`../qwen3_4b_dsa/data_plan.md` §1.

**Target: Phase 2b** (base unfrozen; LM loss + selected-set KL + a minority BC share) at a **32,768-token
training window**. Both decisions are the user's, 2026-07-30. The window drives §5.1 (generation window
== training window) and 2b drives §9.1 (the mixture, and why the BC share stays a minority).

Status: **plan only.** Nothing generated as of 2026-07-30.

#### What "duplicate" means here

**Two or more rows whose prompt text is byte-identical after the `"user: "` strip.** Not
near-duplicates, not paraphrases — the same string.

- **4,791 distinct prompts appear more than once** (3,509 twice, 832 three times, 253 four times, up to
  one appearing **12×**), which is **6,814 redundant rows**. Unique prompts: 95,212 of 102,026.
- **Cause: AI2 concatenated upstream RLVR mixtures without cross-source dedup.** The same competition
  problem was independently collected into several of them, so it arrives 2–4 times:

  ```
  "What is the smallest three-digit number in Pascal's triangle?"      gt=['100']
      AceReason-Math_filtered-request-350-88     · AceReason-Math
      MathSub-30K_filtered-request-1-60          · MathSub-30K

  "How many roots does the equation $\sin x = \frac{x}{100}$ have?"    gt=['63']
      AceReason-Math_filtered-request-52-36      · AceReason-Math
      rlvr_orz_math_57k_collected-request-464-74 · ORZ-math-57k
  ```

  4,089 of the 4,791 groups carry **identical `ground_truth`**, confirming they are the same item; 702
  differ, and those are open-ended WildChat prompts where `ground_truth` is a free-text reference answer
  rather than a verifiable key. 7 groups span two different slices.
- The 12× case is a junk prompt worth knowing about: `"translate to English, don't change symbol and
  line break…"` with **no text attached**, appearing 11× from WildChat plus once from tulu-rewritten,
  each with a different reference answer (all of them variants of *"you didn't provide the text"*).

#### Decision: exact-match dedup, one row per unique prompt string

**We generate over unique prompts only — 93,889 of them, one sample each** (times the explicit,
logged `n` per slice, §9.1). Dedup runs *before* generation, so a duplicated prompt never becomes
duplicated GPU time. The kept copy is the first occurrence in shard order (deterministic under the
seed); which copy wins is immaterial since the text is identical by definition — only the recorded
`original_dataset` provenance label differs.

**Exact match is deliberately not normalised.** A normalised hash (lowercase, collapse whitespace,
strip punctuation) would remove only **302 more rows (0.32 %)** — and it is actively unsafe:

```
# genuine near-duplicate -- normalisation would correctly merge these
"… f(x1) ≤ f(x2) when 0 ≤ x1 < x2 ≤ 1 …"
"… f(x1) <= f(x2) when 0 <= x1 < x2 <= 1 …"

# DIFFERENT PROBLEMS -- normalisation merges them by deleting the minus sign
"… where a,b,c <= 3^2 and  2a^3 + 1b^3 + -1c^3 = 0 (mod 3^3) …"
"… where a,b,c <= 3^2 and -2a^3 + 1b^3 + -1c^3 = 0 (mod 3^3) …"
```

On a math-heavy bank, punctuation *is* semantics. 0.32 % is not worth a filter that silently discards
distinct problems, so **exact match stands.** (Normalised hashing is still the right tool for §8
decontamination, where a false positive costs one dropped training prompt and a false *negative* costs
the validity of a gate.)

**Why dedup before generating**, given that we only use prompts:

1. **Unlogged `n>1`.** Generating over the raw file samples the *same* prompt 2–12 times while the run
   log says `n=1`. That silently up-weights duplicated items in the BC target and makes the effective
   mixture unreproducible.
2. **Pool size is overstated** — the decode-long pool is 44,911, not 51,471 (above).
3. **Self-inflicted val leakage.** Any held-out split taken after generation would share prompts with
   train.

## 2. Why this bank is the right S2/S3 source

The §2 selection criterion in `data_plan.md` is **difficulty, not length**. An RLVR prompt bank is
difficulty-selected *by construction*: AI2 built it by keyword/topic filtering, execution-based
test-case validation, and F1-score filtering, explicitly to keep prompts that a 32B thinking model
does not trivially solve. That is the difficulty prior the data plan says to buy rather than mine.

Concretely, versus the alternatives already surveyed in `data_plan.md` §3:

| | Dolci-Think-**RL**-32B | Dolci-Think-**SFT**-32B | Magpie-Llama-3.3-Pro |
|---|---|---|---|
| prompts | 102K | ~1.1M | 1M |
| difficulty-filtered | **yes, RLVR-grade** | no | self-reported labels |
| license | ODC-BY | AI2-open | **Meta Llama 3.3 Community** |
| hard-math / hard-code share | **50 %** | small | needs mining |

So: **Dolci-Think-RL is the decode-long (S3) engine**; its 51,471 math+code prompts are the ones
that will produce 8–32K traces. It is *not* big enough to also carry the short half at n=1 (§9).

## 3. Slice policy — and one contamination caveat that changes the mixture

| slice | rows | role | recommended share of the generated set |
|---|--:|---|--:|
| Math | 30,182 | **S3 decode-long engine** | use all, n≥1 |
| Code | 21,289 | **S3 decode-long engine**; code is the most sparsity-sensitive *and* most BC-fragile domain (`docs/dsa_eval_report.md` §3) | use all, n≥1, keep ≥20 % of the long share |
| General | 20,708 | **S2 short half.** virtuoussy multi-subject + tulu-rewritten + **WildChat real user traffic** | use all, n≥2 |
| IF | 29,847 | short, but see below | **cap at ≤10 % of prompts (≈10K)** |

> **The IF slice is IFEval-format.** `IF_multi_constraints_upto5_filtered` is built from the same
> verifiable-constraint family that **IFEval** scores, and IFEval is in our Tier-4 short-context
> regression suite (`../qwen3_4b_dsa/eval_plan.md` §2). It is not item-level contamination, but
> training on 29,847 IFEval-shaped prompts and then reporting IFEval as a *regression* check is not
> a clean measurement — in 2b, where the base unfreezes, it could move IFEval *up* and mask real
> drift elsewhere.
>
> **Decision: cap IF at ~10K prompts, and if any IF data is used, report IFEval with the caveat
> stated in the run log.** The short bucket is better served by the General slice (real traffic,
> broad domains, no gate overlap).

If the short bucket still comes up short after this cap, the top-up source is **Dolci-Think-SFT-32B**
(`data_plan.md` §3), which the prompt-source backend in §7 should support from day one rather than as
a retrofit.

## 4. Prompt extraction contract

Per row, in this order:

1. `text = row["prompt"]`; strip a leading `"user: "` (assert 100 % hit rate, fail loudly if the
   dataset changes).
2. **Drop rows containing `\nassistant:` or a second `^user: `** (~1.6 %). They are flattened
   multi-turn, and multi-turn is forbidden for this data — Qwen3's template strips reasoning from
   every assistant turn before the last user query (§6), so a multi-turn BC row silently trains on a
   history whose traces have been deleted. Log the drop count. (Reconstructing them into real
   `messages` is possible but not worth 1.6 %.)
3. `min_prompt_chars=16`, `max_prompt_chars=12_500` hygiene bounds (§1 max is 12,322).
4. `prompt_sha256 = sha256(cleaned_prompt)` — the dedup key and the `--exclude-sha` key, identical in
   meaning to the MiniCPM3 pipeline.
5. Dedup within the run, then apply `--exclude-sha` (prior runs, and the eval-set hashes from §8).
6. Emit one JSONL row: `{source_uid: custom_id, source_dataset, source_config: dataset_source,
   domain: one of Math|Code|IF|General, lang: "en", prompt_sha256, ground_truth (metadata only),
   messages: [{role:"user", content: cleaned}]}` — i.e. **exactly the schema
   `gen_trajectories.py` already consumes.** No downstream change needed for the prompt side.

| knob | value | why |
|---|---|---|
| model | `/cb/ml-eng/aarti/models/qwen3_4b_thinking_2507` | on disk |

| `max_tokens` | **per row: `32768 − prompt_tokens − 11`** | **Decision (2026-07-30): the generation window equals the training window (32,768).** Phase 2 trains at 32K, so a longer generation window would only manufacture rows that get thrown away. Replaces the per-domain `DEFAULT_CAPS` mechanism with a per-row budget — see §5.1 |
| `max_model_len` | **32768** | same window. Worst-case prompt is ~3,330 tokens (§1), so even the longest prompt still gets a ~29.4K trace budget |
| `n` | Math/Code **1**, General **2–4**, IF **1** | §9 budget |
| `seed` | fixed per run, recorded | reproducibility |
| parallelism | `--data-parallel-size 8 --tensor-parallel-size 1` | DP=8 is the measured optimum for a 4B model |
| chunking | `--chunk-size 512` (append + resume) | already implemented; a multi-hour generation will be interrupted |

**Never pass `enable_thinking=False`** anywhere in this pipeline. `add_generation_prompt=True` on
this model emits `<|im_start|>assistant\n<think>\n`, so the completion begins *inside* the reasoning
block and contains only the closing `</think>`. That asymmetry drives §6.

### 5.1 The 32K window, exactly

Verified token IDs (`tokenizer.json` / `tokenizer_config.json` of the local checkpoint):
`<|im_start|>` 151644 · `<|im_end|>` 151645 (also `eos`) · `<think>` 151667 · `</think>` 151668 ·
`user` 872 · `assistant` 77091 · `\n` 198 · `\n\n` 271 · `<|endoftext|>` 151643 (`pad`).

The prefix wrapper is **10 tokens** and the closing `<|im_end|>` is **1**:

```
151644  872   198   [prompt]   151645  198   151644  77091  198   151667  198
  ^im_start user  \n              im_end  \n   im_start assist \n  <think>  \n
```

| | tokens |
|---|--:|
| training window (Phase 2) | **32,768** |
| − prefix wrapper | 10 |
| − closing `<|im_end|>` | 1 |
| − prompt (measured p50 / p99 / max, §1) | 117 / 957 / 3,202 |
| **= `max_tokens` (p50 / p99 / worst case)** | **32,640 / 31,800 / 29,555** |

Measured over all 93,889 prompts: generation budget p50 **32,640**, minimum **29,555**;
**0.000 % of prompts leave less than 8,192 tokens of budget**, and **0.000 % exceed the window**. So
every prompt in the bank can reach the decode-long bucket, and the window costs us nothing on the
input side.

Consequences of tying the two windows together:

- **No row is ever discarded for exceeding the training length** — the sampler cannot produce one.
  The 32K cap stops being a filter and becomes a *generation budget*.
- The only length-related yield question left is the **`finish_reason == "length"` rate**: traces that
  wanted more than ~30K. That is now the single headline pilot number (§11.2).
- `gen_trajectories.py`'s per-domain `DEFAULT_CAPS` no longer applies. It needs a
  `--fit-window 32768` mode that computes `max_tokens` per request from that row's prompt length.
  Prompts are tokenized during prompt-selection anyway, so the number is already in hand.

## 6. The tokenization contract — the landmine, and the decision it forces

Verified by rendering the local model's Jinja template directly:

```
GEN PROMPT [user]  -> '<|im_start|>user\n2+2?<|im_end|>\n<|im_start|>assistant\n<think>\n'
FULL [user,asst]   -> '<|im_start|>user\n2+2?<|im_end|>\n<|im_start|>assistant\n<think>\nreasoning here\n</think>\n\nFinal answer: 42<|im_end|>\n'
ASST ALONE         -> '<|im_start|>assistant\nFinal answer: 42<|im_end|>\n'          <-- trace DELETED
```

`MultiTurnSFTDataset._process_single_message` calls `apply_chat_template(messages=[message])` — **one
message at a time**. With no user turn in that render, `ns.last_query_index` degenerates and the
template takes the reasoning-stripping branch. Feeding BC trajectories through the default SFT
dataset would therefore train on the final answer only, silently discarding >95 % of the tokens and
the entire capability being preserved. Storing the trace in a `reasoning_content` field does **not**
help: the strip decision is made by the branch, not by where the trace is stored.

Two more reasons not to route this data through `MultiTurnSFTDataset`:

- Phase 2 already runs on **`PackedPretrainDataset`** (`examples/msa/run_qwen3_msa_phase2.sh`), which
  reads `input_ids` and ignores any `loss_mask` column (it emits all-ones) and **drops every row
  shorter than `seq_len`** — so BC rows would be silently discarded too.
- We want byte-exact parity between the training render and the serving render.

> **Decision: build `input_ids` by splicing the served prefix with the sampled completion tokens.**
>
> ```python
> prefix_ids = tok.apply_chat_template([user], add_generation_prompt=True, tokenize=True)  # what vLLM was given
> input_ids  = prefix_ids + list(completion.token_ids) + [151645]                          # + <|im_end|>
> loss_mask  = [0] * len(prefix_ids) + [1] * (len(input_ids) - len(prefix_ids))
> ```
>
> Three properties, none of which the re-render path gives for free:
>
> 1. **Training prefix == serving prefix, by construction** — it is the same call, not a
>    reconstruction that happens to agree.
> 2. **The trace tokens are exactly what the model sampled.** Decoding a completion to text and
>    re-encoding it does **not** reliably round-trip under BPE (whitespace runs, digit groupings,
>    partial-token boundaries). Re-tokenizing would train the indexer on a token sequence the target
>    never emitted — a small, silent off-policy leak in a pipeline whose entire point is being
>    on-policy.
> 3. The reasoning-stripping template branch is **never reached**, rather than worked around.
>
> Cost: `gen_trajectories.py` must persist `completion.token_ids` (it currently keeps only the text
> and the counts) — one field, §10.
>
> **The full-render diff survives as a test, not as the production path:**
> `full_ids = tok.apply_chat_template([user, {"role":"assistant","content":"<think>\n"+text}])` must
> satisfy `full_ids[:len(prefix_ids)] == prefix_ids` and agree with the spliced `input_ids` up to
> known-benign whitespace canonicalisation. This is also why §4 drops multi-turn rows —
> prefix-monotonicity fails as soon as an earlier assistant turn's reasoning gets stripped.

## 7. Filters — malformed responses

**Yes, malformed responses are dropped, and the check runs on token IDs, not text.** Because §6 keeps
`resp_token_ids`, every structural test below is an exact integer test — no decode/re-encode ambiguity,
no regex on model prose. Thinking models fail in structural ways that a plain SFT pipeline does not
look for, and in 2b the base trains, so a malformed row is not merely wasted — it teaches the failure.

Marker IDs: `<think>` 151667 · `</think>` 151668 · `<|im_start|>` 151644 · `<|im_end|>` 151645.

| class | detection (on `resp_token_ids`) | policy | why |
|---|---|---|---|
| **unfinished trace** | `finish_reason == "length"` | **2b: drop · 2a: keep** | rode the 32K window; teaches non-termination under an LM loss, but is excellent KL supervision (§9) |
| **no `</think>`, yet stopped** | `151668 not in ids` and `finish_reason == "stop"` | **drop** | emitted EOS *mid-reasoning* — there is no answer segment at all. A distinct pathology from hitting the window; count it separately |
| **multiple `</think>`** | `ids.count(151668) > 1` | **drop** | the served format has exactly one; the template's `split('</think>')` would mis-parse, so training and serving formats diverge |
| **re-opened `<think>`** | `151667 in ids` | **drop** | the model restarted reasoning mid-answer; the prefix is already inside a think block, so this is malformed by construction |
| **empty answer** | no non-whitespace token after `151668` | **drop** | reasons and then says nothing — a real thinking-model failure, and cloning it is actively harmful |
| **role-marker leakage** | `151644 in ids` or `151645` before the final position | **drop** | template break or an injected turn from the source prompt; would corrupt the conversation structure |
| **repetition loop** | any 32-token n-gram repeated ≥8×, or >30 % of the trace covered by repeats | **drop** | `data_plan.md` §6; the classic long-trace degeneracy |
| **empty / stub** | `len(ids) < 8` | **drop** | |
| **no reasoning at all** | `</think>` within the first ~8 tokens | **keep, but log** | legitimate for a trivial prompt; if the rate is non-trivial on this difficulty-filtered bank, something is wrong with the sampling config |
| **over-window** | `len(input_ids) > 32768` | **assert, do not filter** | impossible under §5.1 — if it fires, the window plumbing is broken and silently dropping rows would hide it |

Every class gets a **counter in the report, per subset**. A rate that moves between runs is the
earliest signal that a sampling knob drifted.

Two policy notes:

- **Never filter on answer correctness** (`data_plan.md` §6). Malformedness is about *structure*, not
  about being right. Rejection sampling on correctness would shift the data off-policy and defeat the
  entire point of behavior cloning. `ground_truth` feeds the diagnostic log only.
- **Drop, do not repair.** Truncating a row back to its last valid `</think>`, or appending a synthetic
  answer, manufactures a sequence the target never produced.

### 7.1 Length and bucketing filters

| filter | policy |
|---|---|
| **truncated** (`finish_reason == "length"`, or no `</think>`) | **Phase 2b: drop** — traces that ride the window teach the model not to terminate (`data_plan.md` §6). **Phase 2a: keep** — 2a is indexer-only, the LM loss is a measurement, and the selected-set KL over a ~32K unfinished trace is excellent attention supervision (it is, in fact, the *longest* data in the mixture and lands squarely in the k/L regime we care about). The `--keep-truncated` flag already exists; emit **both** parquets from one generation run. **Log the rate per slice — under §5.1 this is the only length-related yield number, and it is the headline pilot measurement.** |
| **degenerate / looping** | new n-gram repetition detector (e.g. any 32-token n-gram repeated >8×, or >30 % of the trace inside repeats). Not implemented today — §10 |
| **too short** | `total_tokens >= 2048` for rows destined for the *long* buckets; keep short rows in the short bucket (below `k` a sequence runs effectively dense and yields no sparse signal, but it is still valid short-context BC) |
| **correctness** | **never filter.** Log accuracy against `ground_truth` as a diagnostic only (§9) |

Bucketing is **post-hoc on realized length** (`data_plan.md` §2), via `analyze_lengths.py`:
short `<4K` · decode-long `8–32K` · (prefill-long comes from S1).

### 9.1 The Phase-2b mixture — resolving a conflict between two plan sections

**Target: 2b** (user, 2026-07-30). Two existing statements do not fit together:

- `../qwen3_4b_dsa/data_plan.md` §5: **40 % short / 30 % decode-long / 30 % prefill-long** — i.e. 70 %
  of sequences come from *generated* data.
- `../qwen3_4b_dsa/plan.md` §6.2: 2b's loss is **LM loss on real docs (dominant)** + selected-set KL
  **+ a *smaller* BC self-distillation share** — because BC self-distillation is what cost **−3.0 on
  HumanEval+** in the MiniCPM3 run, more than double the −1.3 sparsity cost (`docs/dsa_eval_report.md` §3).

They conflict only because §5 is about **sequence length** and §6.2 is about **objective and drift**.
The resolution is to stop treating "short" as a synonym for "generated":

> **Short real-document windows cost nothing and carry no drift.** The InfLLM corpus is already built;
> re-windowing it at 4K instead of 32K is one flag on `examples/dsa/prepare_real_data.py`, needs no
> generation, and trains under the pretraining objective. Decode-long is the *only* bucket that
> genuinely requires self-generated traces, because no corpus contains "Qwen3-4B-Thinking's own CoT".

Recommended 2b mixture at a ~1B-token budget:

| bucket | share | tokens | source | rows @ avg len | objective |
|---|--:|--:|---|--:|---|
| prefill-long 32K | 30 % | 300M | **S1 real docs** (`infllm_qwen3_32768_train.parquet`, 15,000 windows exist) | ~9,200 @ 32,768 | LM + KL |
| decode-long 8–32K | 30 % | 300M | **BC: Math + Code traces** | ~25,000 @ ~12K | LM (masked) + KL |
| short — real | 25 % | 250M | **S1 re-windowed at 4K** — new, free, no generation | ~61,000 @ 4,096 | LM + KL |
| short — BC | 15 % | 150M | **BC: General + the short tail of Math/Code** | ~60,000 @ ~2.5K | LM (masked) + KL |

**BC total = 45 %** — a minority, satisfying §6.2 — while the length distribution still matches §5
(40 % short / 30 % decode-long / 30 % prefill-long). Code stays ≥20 % of the long share.

This also **shrinks the generation job**: only Math + Code + General are needed.

| | usable prompts | n | est. tokens |
|---|--:|--:|--:|
| Math | 24,153 | 1 | ~290M |
| Code | 20,758 | 1 | ~145M |
| General | 19,134 | **2** | ~77M |
| **generate** | **64,045 prompts / 83,179 samples** | | **~510M** |

Of which ~400M lands in decode-long (target 300M — healthy margin for §7's filters and the truncation
uncertainty) and ~110M in short-BC (target 150M — a modest shortfall). `n=2` on General is what closes
most of that gap; if the realized short-BC share still misses, raise **short-real** from 25 % to 30 %
rather than generating more BC, since short-real is free and drift-free.

**Dropping the IF slice entirely is now the recommendation, not just a cap** (§3): with short-real
carrying the short bucket, IF's only contribution would be IFEval-shaped prompts feeding a run whose
base trains and whose regression suite includes IFEval. The measurement is worth more than the tokens.

**Decision (user, 2026-07-31): 2b only — do not emit the 2a parquet.** The `--keep-truncated` pass is
skipped; the full run produces a single `bc_2b.parquet` with truncated rows dropped per §7.

Note what is and is not optional here. The **splice is mandatory** — it is what converts
`trajectories.jsonl` (prompt + response *text*) into the trainable
`input_ids` / `loss_mask` arrays, and it is the only path that preserves `<think>` (§6). What the 2b-only
decision drops is the *second filter pass*, not the tokenization.

Consequence to keep in view: dropping `finish_reason == "length"` removes ~7 % of rows, and they are
**the longest ones** — full-32K sequences concentrated in Math/Code, i.e. exactly the decode-long regime
sparse attention is being trained for. That is still correct under an LM loss (a trace that never
terminates teaches non-termination), and §11.2 shows the pool is large enough without them: 88 % of Math
and 52 % of Code rows land in the 8–32K band. Revisit only if the realized decode-long share undershoots
the §9.1 target of 30 %.

**Two bugs the pilot caught** (both fixed; neither would have thrown):

- **transformers 5.3.0 changed `apply_chat_template(tokenize=True)` to return a `BatchEncoding`**, so

  first run's `prefix_rebuild_differs = 96/96` counter is what exposed it; it is now **0**.
- **vLLM 0.20.2 cannot accept `prompt_token_ids` under transformers 5.3.0** —
  `_validate_model_input` does `max(tokenizer.max_token_id, vocab-1)` and `max_token_id` is a `str`
  → `TypeError`. Now we pass the templated **string** and record the engine's own returned
  `o.prompt_token_ids` as the authoritative prefix, which is a stronger guarantee than tokenizing it
  ourselves.

### 11.1 Pilot preparation and the two launch blockers (2026-07-30)

The 100-prompt set is built and the pipeline is wired end to end; **generation is deferred until the
GPUs are free** (user's call). Artifacts:
`/cb/ml-eng/aarti/dsa/qwen3_ph2b_pilot_20260730_212850/{prompts.jsonl,launch_gen.sh}` — 25 each from
Math / Code / General / IF (IF is measurement-only, §9.1), prompt tokens 9–1,011.

Two launch blockers were found by attempting it, both now handled:

1. **The node is shared.** `ml-eng-gpu-08` had another container holding **61.5 GB and 15–93 % util on
   all 8 GPUs**, leaving ~17.7 GB free each, so `gpu_memory_utilization=0.9` fails at engine init with
   `Free memory on device cuda:0 (18.6/79.18 GiB) … less than desired`. It is *not* visible via
   `nvidia-smi --query-compute-apps` from inside our container — only the per-GPU `memory.used` shows
   it. **Always check `memory.used`, not the process list, before sizing a run.** Fitting inside the
   remainder (`--gpu-memory-utilization 0.21`) works but leaves only ~7 GB of KV cache ≈ 1.4 concurrent
   32K sequences, and the throughput number would be contended, hence useless for the §9 estimate.
2. **DP replica port collision — a real defect in the launcher, independent of GPU availability.** The
   8 single-GPU engines each opened their own `torch.distributed` TCPStore and raced through
   `get_open_port()`; the losers died with
   `DistNetworkError: … port: 36683 … EADDRINUSE`. **Fixed:** `launch_dp` now hands each replica a
   disjoint port block (`VLLM_PORT = --vllm-port-base + rank*16`) and staggers spawns by
   `--launch-stagger` (default 3 s). This would have hit the 64K-prompt run too.

When the GPUs are free, the pilot is one command — `$RUN/launch_gen.sh` (it records `git_sha.txt` +
`git_diff.patch` next to the outputs, per `memory:log-full-invocation`), then §12 steps 4 and 6.

## 13. Open decisions

1. ~~**Short-half top-up**~~ — **resolved by §9.1**: the short bucket is carried by real-document 4K
   windows (free, no drift), not by `n>1` sampling or a second prompt bank. Dolci-Think-SFT is no
   longer needed; keep the backend stub anyway, it costs nothing.
2. ~~**IF slice cap**~~ — **resolved by §9.1**: drop IF entirely. Its only role was the short bucket,
   which short-real now covers, and it is IFEval-shaped while IFEval is a 2b regression gate.
3. **How much truncation is acceptable in the math slice** (§9, §11.2). If it lands >30 %, the choice
   is: accept a thinner decode-long pool, spend the surplus on `n=2` over Math, or raise the training
   window above 32K — the last is excluded for now by the 32K decision.
4. **Whether 2b needs the BC share at all.** 45 % (§9.1) is a *recommendation*, not a measurement. The
   cheapest experiment is a 2b variant at BC = 0 % (pure real-doc LM + KL): if the sparsity cost
   recovers without BC, the MiniCPM3 −3.0 HumanEval+ drift is avoided outright. Worth an ablation slot
   given that BC is the only drift-carrying component in the whole mixture.
